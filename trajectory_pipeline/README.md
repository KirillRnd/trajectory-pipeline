# Общие модули

## R-преобразование

Модуль `r_transform.py` работает с любым узлом дуги, заданным
безразмерным состоянием `[r, v]`. Для переноса между узлами привести
оба состояния к общим единицам и осевому базису. В `legacy` строки
`B` равны `r, v, r×v`. `angular` нормирует длину каждой строки,
сохраняя угол между `r` и `v`. В `rtn` строки ортонормированы.

`transport_matrix` строит `Q = B_target⁻¹ B_ref`.
`transport_costates` применяет `Q` к `p_r, p_v`, а
`transport_vector` применяет `Q⁻ᵀ` к двойственному вектору.
Эта пара сохраняет скалярное произведение. Пространственный перенос
оставляет `p_m` скаляром. При смене нормировки задачи или функционала
отдельно пересчитывать масштабы сопряжённых. Формулы `date_sweep._seed`
относятся к физической ПСИ при α=β=1.

Для решения краевой задачи непосредственно в R-координатах передать
`costate_frame=orbital_frame(state, kind)` в
`irt.correct_shooting`, `bounded.collocate` или `bangbang.solve_bangbang`.
Матрица фиксируется на время коррекции и может строиться по внутреннему узлу.
Корректоры вычисляют динамику, граничные невязки, условия переключения и
результаты в исходных физических координатах задачи. Без опции используется
декартов подбор.

Диагностика чувствительности и переноса из узлов сохранённой дуги:

```powershell
docker compose run --rm --entrypoint python pipeline -m trajectory_pipeline.r_study --trajectory data/benchmarks/psi/earth_venus_2032 --fractions 0 0.3 0.7 --output runs/venus_r_nodes
```

Без `--trajectory` команда воспроизводит контрольную серию. В
`results.json` записываются спектры в разных координатах, угол между
`r` и `v`, проверка шага дифференцирования и невязки после переноса.
Для точных дуг диагностический якобиан рассчитан при фиксированном
расписании переключений. В [отчёте](../reports/r_transform_study.md)
описаны контрольные задачи, условия применения и измеренные границы.

## Быстрый перебор дат ПСИ

`sweep-psi` принимает каталог проверенной гелиоцентрической ПСИ с центральным
полем Солнца. Поддерживается межпланетный участок между телами. Режимы с
раскруткой, импульсами и захватом идут через `solve` или `sweep-solve`.
Границы диапазона задаются в TDB. Шаг по умолчанию равен одним суткам.
Длительность перелёта, аппарат, закон тяги и ограничения наследуются из опоры.
Эфемериды обоих тел должны покрывать весь диапазон от первой даты отправления
до последней даты прибытия для штатного пересчёта и его графиков.

```powershell
docker compose run --rm pipeline sweep-psi data/benchmarks/psi/earth_venus_2032 --start 2032-10-30 --stop 2032-11-03 --output runs/venus_daily
```

Каждый расчёт независимо берёт одну и ту же опору. Для новой даты вычисляются
эпохи, состояния тел и `Q = R_date⁻¹ R_ref` по соглашению `venus_cycle.m`.
`Q` переносит векторные сопряжённые переменные, `Q⁻ᵀ` переносит начальное
приращение скорости. Сопряжённые переменные учитывают новую нормировку.
Моменты переключений опоры дают начальное приближение для точной стрельбы
при α=β=1. Корректор использует новые граничные состояния и реальные F/c.
Приёмка включает независимое интегрирование, аудит запроса и сверку с KIAM.

`--fast-budget-s` задаёт бюджет коррекции одной даты, по умолчанию 10 секунд.
Если быстрая попытка сорвалась или не прошла проверку, соответствующая дата
идёт в стандартный `solve` через `sweep-solve`. Туда же идут выбросы расхода.
Для каждой принятой даты локальный тренд строится как медиана линейных
прогнозов по парам среди шести ближайших других принятых дат. Порог равен
максимуму `--outlier-abs-kg` (0.5 кг) и `--outlier-rel` (0.05) от модуля
прогноза. Оценка применяется от трёх принятых дат и отмечает отклонения в обе
стороны. Это правило выделяет локальные выбросы расхода.

В `fast/` хранятся R-преобразования, запросы, принятые решения и журналы
быстрых попыток. В `standard/` сохраняются штатные пересчёты, а в
`results.csv` и `results.json` указаны причина пересчёта, расход и время
каждой попытки и путь к выбранному решению. Если приняты оба решения,
выбирается меньшее по расходу. При разнице до 0.0001 кг предпочтение
отдаётся стандартному. Если пересчёт выброса остановился, быстрый артефакт
сохраняется со статусом строки `review_required` и пустым выбором.
Выход 0 означает, что приняты все даты, выход 2 оставляет незавершённые
или требующие проверки строки. `--resume` продолжает серию с теми же
исходниками, настройками, опорой и окружением по сохранённым попыткам.

## Четыре сочетания орбитальных манёвров

Новый общий вход `orbital_maneuvers` независимо задаёт `departure.kind`
и `arrival.kind`: `spiral` или `impulse`. `solve` направляет такую миссию
в `orbital_pipeline.py`; она не смешивается с прежними полями
`parking_departure` и `capture`.

Обязательное `mass_reference="initial_orbit"` означает массу КА на исходной
НОО. Раскрутка использует аппаратные F/c и прямое интегрирование с расходом;
межпланетная ПСИ получает фактическую меньшую массу. При импульсном отлёте
внешний РБ не расходует топливо из массы полезной нагрузки. Импульсный захват
использует собственное `arrival.exhaust_velocity_m_s`, и его топливо входит
в исходную массу КА. Полная масса/топливо внешнего РБ остаются вне модели.

Параметры `departure` соответствуют исходной круговой орбите; `arrival` —
конечной эллиптической орбите и сфере. Импульсное прибытие дополнительно
задаёт положительный `arrival.excess_velocity_m_s` входящей гиперболы.
Скорость истечения химического двигателя не берётся из `spacecraft` ЭРДУ.
См. восемь явных конфигураций и две одинаковые по правилам матрицы
в `configs/orbital_modes/`.

Эпоха `launch_tdb` по-прежнему относится к выходу из сферы Земли,
`tof_days` — к межпланетному участку. Раскрутка начинается раньше;
скрутка или пролёт до импульсного захвата завершаются позже прибытия на сферу.
При смене свободного отлёта на заданное состояние контроллер строит новую
штатную цепочку ИРТ → Пазов → ПСИ, не фиксируя старое число активных дуг.

Выход: `departure/`, `outer/`, `arrival/`, `final/`, запросы и `impulses.json`.
Локальные интерфейсы непрерывны по состоянию, времени и массе. На самом
импульсе проверяются векторный скачок скорости и ракетное уравнение массы.
Конец `arrival/` при импульсном захвате — до включения; конец `final/` — после.

```powershell
docker compose run --rm pipeline solve configs/orbital_modes/mars_spiral_impulse_dry60.json --output runs/new_orbital_case
docker compose run --rm pipeline verify-orbital runs/new_orbital_case
docker compose run --rm pipeline render-orbital runs/new_orbital_case --output runs/new_orbital_plots
```

`verify-orbital` проверяет обе границы, массу/тягу, независимый пересчёт
локальных участков, ПСИ/KIAM, конечную орбиту, события и композицию массивов.
`render-orbital` только читает данные; мгновенный расход рисуется скачком.
Готовое решение можно проверить через `--resume`; частичное возобновляется
с принятого физического checkpoint внешней ПСИ. Без такого checkpoint
возобновление отклоняется, прежние результаты сохраняются.

Две серии с сухими массами 90 и 60 кг разделены: вторая проверяет реализацию
всех режимов, а не заменяет исходный аппарат ради доли успеха. Частичный путь
не доказывает физическую недостижимость. Все режимы сохраняют приближение
сопряжённых центральных полей и не доказывают совместный глобальный оптимум.

## Отлёт с круговой НОО и импульс РБ

Поле `parking_departure` подключает `launch_pipeline.py` в обычном `solve`.
Параметры: `parking_altitude_m` (типичное значение по умолчанию 200000 м),
`interface_radius_m`, `planet_radius_m`, `mu_m3_s2`, `plane_mode="free"`.
Высота настраивается в миссии; в решателе она не зашита. Пример:
`configs/earth_mars_2030_dec01_leo200_capture.json`.

`launch_tdb` в этой постановке — эпоха выхода из сферы Земли, а не импульса
на НОО. Эпоха импульса вычисляется вычитанием пролётного времени. Контроллер
согласует положение на конечном радиусе и полный вектор скорости с новой
межпланетной ПСИ; при заданном `capture` пересчитывает и массовую сшивку
с прибытием. `departure_offset_state_si` — внутренняя разрешённая граница.
`vinf_max_m_s` остаётся пределом истинного избытка; при конечном радиусе
граница скорости преобразуется по энергии гиперболы.

Выход: `launch/`, `match_NN/`, `final/`, `coupling.json`, независимая проверка
и отдельные графики. `--resume` проверяет готовую миссию либо продолжает
с сохранённого согласования, не меняя входные параметры.
Импульс мгновенный, плоскость свободна; масса КА — полезная нагрузка после
отделения РБ. Топливо РБ без его удельного импульса и сухой массы не вычисляется.
Полная постановка и ограничения: `reports/examples/mars_dec2030_leo200.md`.

## Планетоцентрический захват

`solve` с полем `capture` запускает общий контроллер
`capture_pipeline.py`: обратная скрутка → согласование межпланетной границы
и массы → прямое распространение → проверка сшивки и конечной орбиты.
Пример: `configs/earth_mars_2030_dec01_capture_400x30000.json`.
Размеры задаются в СИ: μ, радиус планеты, высоты перицентра/апоцентра,
радиус интерфейса. Двигатель и масса берутся из той же миссии. Поле
`arrival_offset_state_si` — разрешённая шестимерная граница внешнего участка;
при захвате её вычисляет контроллер, а не старый центр планеты.

Текущий закон — непрерывное поперечное торможение, как в раннем
`integrate_equinoctial.m`, с физическими постоянными F/c и переменной массой.
До тяги добавлен пассивный участок от апоцентра на границе. Геометрия:
плоскость орбиты планеты, прямое движение и вход с солнечной стороны;
произвольный гиперболический вход пока не поддерживается. Поля центральные,
сопряжённые; это не N-body и не совместный глобальный оптимум.

Результат сохраняет `outer/`, `capture/`, `final/`, `outer_request.json`,
`coupling.json`, независимую проверку и графики. `--resume` поддерживает
готовый результат и восстановление распространения после согласования массы.
Неудача сохраняет конкретную `capture_phase` и `stop_kind`.
Без `capture` результат имеет область `heliocentric_segment`; он не означает
выход на планетную орбиту. Прежние широкие матрицы проверяли эту область.
Подробности и ограничения: `reports/examples/mars_dec2030_capture.md`.

## Параметры запроса и приёмка результата

Новый запуск сохраняет `request.json`: разрешённые значения параметров,
эпохи, длительность, граничные состояния и нормировку. Его контрольная сумма
отличается от SHA только численных массивов. На каждом стыке ИРТ → начальная
скорость → Пазов → ПСИ проверяется соответствие результата этому запросу;
журнал — `parameter_audit.json`. Поля `configuration_sha256` наследуются
результатами и обнаруживают случайное изменение метаданных по дороге.

Финал дополнительно восстанавливает F и c из безразмерных коэффициентов,
сверяет физическую массу, профиль тяги/ускорения, сухую массу и расход F/c.
Проверяются исходные даты, длительность, состояния тел и нормировка.
Устаревшая траектория с другим двигателем не становится готовой только из-за
замены `mission.json` или флага `hardware_limit_reached`.
Неизвестные поля двигателя и нечисловые/неположительные параметры отклоняются
до расчёта; параметры не подменяются молчаливыми значениями по умолчанию.

`configs/parameter_study_design.json` задаёт 24 случая: Венера, Марс, Апофис,
Церера × одинаковые шесть вариантов: исходный, F×2, c×2, m₀×2 (с той же
долей сухой массы), старт +90 суток, длительность ×1.2. Численные правила
одинаковы; параметры изменяются по объявленному плану для всех базовых миссий.

```powershell
docker compose run --rm pipeline parameter-matrix configs/parameter_study_design.json --output runs/parameter_matrix.json
docker compose run --rm pipeline sweep-solve runs/parameter_matrix.json --parameter-design configs/parameter_study_design.json --output runs/parameter_study_v1
docker compose run --rm pipeline parameter-report configs/parameter_study_design.json runs/parameter_study_v1 --output runs/parameter_study_v1/report.md
```

Отчёт проверяет каждый готовый результат заново относительно запрошенной
конфигурации и показывает долю завершений отдельно по каждому варианту и
каждой базовой геометрии. Частичные пути не учитываются как готовые ПСИ.
Для каждой остановки отчёт показывает конкретный блок и характер отказа;
несходимость отдельных постановок допустима и не требует их подгонки.
Отдельный подробный список без нового расчёта:

```powershell
docker compose run --rm pipeline outcome-report <series> --output runs/stops.md
```

Выходы — Markdown, JSON и CSV: бюджет этапа, минимальный шаг, ошибка Python,
авария рабочего процесса, последняя проверенная модель/артефакт. Формулировка
«физически недостижимо» не выводится из этих остановок.
Ключ `--parameter-design` проверяет матрицу до запуска первого случая.
Числа 156 и 156.0 имеют одну идентичность; строки и логические значения
вместо физических чисел отклоняются. Старые сохранённые контрольные суммы
проверяются с сохранением совместимости.

Завершённая серия: 14 полных / 8 частичных / 2 ошибки из 24. Выводы —
`reports/parameter_study_v1_analysis.md`. Для повторной проверки архива
использовать его снимок плана, а не изменяемые текущие конфигурации:

```powershell
docker compose run --rm pipeline parameter-report data/benchmarks/parameter_study_v1/study_design.json data/benchmarks/parameter_study_v1 --output runs/parameter_study_archive_report.md
```

Запуск из корня проекта через `docker compose run --rm pipeline`. Все расчёты и проверки — в Linux-контейнере; Windows Python не использовать.
Готовность блоков и принятые условия находятся в `../PIPELINE_STATUS.md`.

```powershell
docker compose build pipeline
docker compose run --rm pipeline sweep-solve configs/physical_matrix.json --output runs/physical_matrix_docker_v1
```

Контейнер: Python 3.12 / Debian Trixie, неизменённый Linux wheel KIAM 6.1.6
с готовым Fortran. Базовый образ закреплён digest, Python-зависимости —
`docker/requirements.lock.txt`; SHA256 wheel проверяется при сборке.
NumPy/SciPy и аппарат/матрица сохранены такими же, как в первом проходе.
BLAS/OpenMP используют один поток, одинаково для всей серии.
Серия записывает `environment.json` и сведения об окружении в ИРТ-сводках;
возобновление не смешивает разные Python/OS/зависимости/число потоков.

Обычный сервис работает офлайн: исходники/данные доступны только для чтения,
запись — в `runs/` и `output/pipeline/`. Для явной загрузки эфемерид использовать
сервис `ephemerides`, у которого разрешены сеть и запись в `data/ephemerides/`.
Отчёты из контейнера сначала сохранять в `runs/` или `output/pipeline/`.

## Данные

`Trajectory` хранит JSON с описанием и NPZ без pickle. В массивах используются
метры, секунды, кг и ньютоны. Эпоха — JD TDB, время массива отсчитывается от неё;
центр и система осей обязательны. Сопряжённые переменные хранятся отдельно с
оговорённым соглашением. SHA256 связывает JSON с конкретным NPZ.
Флаг `imported_reference` не означает новую независимую проверку.

## Эфемериды

`Ephemerides.state(body, jd_tdb, center='Sun')` выдаёт геометрические состояния
в осях ECLIPJ2000 в SI. Преобразование из KIAM использует наклонение J2000
84381.448 угловых секунд. Пакет KIAM не изменяется; вызовы сериализованы,
поскольку пакет использует глобальные Fortran-переменные и временно меняет cwd.

Планеты и Луна доступны офлайн из JPLEPH в wheel. Для внешних планет штатная
эфемерида KIAM может описывать барицентр системы, что отмечается в `coverage`.
Загруженная таблица Horizons имеет приоритет. Для Юпитера локально сохранён
именно центр планеты, а не барицентр системы. Разность старых эфемерид KIAM
и современных Horizons не следует путать с ошибкой численного решателя.

Сохранены таблицы 2028-01-01 — 2035-01-01 для Апофиса, Эроса, Бенну, Рюгу,
Полигимнии, Цереры и 2015 RE36 (шаг 12 ч), а также Юпитера (6 ч).
Для Апофиса участок 1–25 апреля 2029 уплотнён до часа, 12–15 апреля — до минуты.
Дополнительно сохранена Веста (Horizons `4;`) на том же интервале с шагом
12 ч как независимая будущая проверочная цель. На 73 отложенных эпохах
измерены максимальные ошибки 0.859 м и 0.00000220 м/с; исходный ответ и
отчёт — `data/ephemerides/validation/vesta_horizons.txt` и `vesta_report.json`.
Это выборочная проверка, не строгая оценка ошибки на всём интервале.
Веста не добавлена задним числом в фиксированные матрицы 15/24 постановок.
Интерполяция Эрмита согласует координаты и скорости; экстраполяция запрещена.
Относительные времена узлов регулярных таблиц очищаются от микросекундного
шума представления больших JD перед вычислением производных.

```powershell
docker compose run --rm pipeline coverage Moon Apophis Jupiter
docker compose run --rm ephemerides cache vesta --start 2028-01-01 --stop 2035-01-01
```

Загрузка использует [официальный Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html).
Сохраняются исходные ответы, параметры запроса и контрольные суммы.
Существующая таблица не перезаписывается обычной загрузкой; для уплотнения
внутри покрытия используется `cache ... --refine --step '1 h'`.
Вычислительные вызовы `state` в сеть не обращаются.

Проверка на независимых от узлов эпохах сохранена в
`data/ephemerides/validation/accuracy_after_refinement.json`:
для семи астероидов на проверенной выборке ошибки менее 12 м и 0.001 м/с,
для Юпитера — 34 м и 0.005 м/с. Это выборочные измерения, не строгая оценка
ошибки на всём интервале. Для проверенных Венеры, Марса и Луны отличие KIAM
от современных Horizons составляет до 310 м; источник граничных условий
нужно сохранять вместе с результатом. Лунные координаты сами по себе не
подтверждают пригодность солнечной двухтельной динамики для полёта к Луне.

## Визуализация

Каждый рисунок новой модели содержит F,c,начальную/сухую массы, старт TDB и
длительность. Промежуточная модель отдельно показывает фактический предел
тяги, α и β; она не подписывается как принятая ПСИ. Исторический УММП
сохраняет собственный заголовок и закон двигателя.

```powershell
docker compose run --rm pipeline render data/references/ummp156 --output output/pipeline/reference
```

Команда работает только с сохранёнными массивами: 2D и 3D траектория,
профили тяги и массы, SVG/PNG и компактные JPEG для проверки. Активные и
пассивные участки разделены, масштаб осей равный, опорные орбиты и маркеры
берутся из сохранённого результата. Отсутствие тягового профиля в данных
не интерпретируется как наличие подтверждённых bang-bang переключений.

Эталон УММП импортирован из уже рассчитанного MAT, скопированного в
`data/references/`. Численная траектория и профиль тяги сохранены точно.
Орбиты для фона построены в исходной двухтельной модели, чтобы не подменять
старое решение новыми эфемеридами. Повторная оптимизация не выполнялась.

## ИРТ и продолжение по избытку

`Mission` описывает тела, календарь TDB, длительность, тип встречи/пролёта,
допуски, аппарат и постановку избытка. `configs/irt_matrix.json` — матрица
12 реальных задач: Венера, Марс, Меркурий, Юпитер, шесть астероидов,
Венера → Земля и пролёт Марса. Эта матрица не охватывает пока Луну,
все даты/длительности и все модели возмущений.

```powershell
docker compose run --rm pipeline sweep-irt configs/irt_matrix.json --output runs/my-irt-series
docker compose run --rm pipeline departure data/benchmarks/irt/earth_apophis_2029 --output runs/my-departure
docker compose run --rm pipeline departure data/benchmarks/irt/earth_apophis_2029 --output runs/my-departure --resume
```

Для одиночного ИРТ-перелёта `solve-irt <mission.json> --output <новый каталог>`;
одиночный JSON содержит одну конфигурацию из матрицы. Для продолжения всей
матрицы — `sweep-departure configs/irt_matrix.json --sources data/benchmarks/irt --output <новый каталог>`.
Каталоги новых расчётов не переиспользуются без явного `--resume`.

ИРТ использует несколько начальных сопряжённых переменных ILTT с преобразованием
в исходную систему координат. Основной корректор — стрельба с вариационным
Якобианом. Резервный маршрут — коллокация с последующим уточнением стрельбой.
Лимит времени действует внутри интегратора, поэтому один трудный кандидат
не блокирует проверку следующих. Проверка другим интегратором входит в
принятие кандидата: одного малого внутреннего остатка недостаточно.
По умолчанию сравниваются найденные варианты по квадратичному функционалу в рамках
бюджета. `solver.compare_seeds=false` явно включает выбор первого принятого решения.
Это не полный перебор ветвей и не доказательство глобального минимума.

Продолжение различает фиксированный вектор (`vinf_vector_m_s`), фиксированный
модуль, ограничение модуля сверху и свободную скорость. Направление на активной
границе согласовано с начальным p_v. На неактивной границе проверяется p_v(t0)=0.
Для свободной ветви предусмотрены коллокация и стрельба по [v0,p_r0] с
вариационными производными. При неудаче шаг уменьшается; принятая точка не
теряется. Возобновление проверяет исходную задачу и источник; новые сеансы
фиксируют хеши кода. `partial` означает незавершённый численный путь,
а не доказанную недостижимость перелёта.

`completed_stage` относится только к выполненному этапу. ИРТ и его продолжение
не учитывают ограничения тяги аппарата и расход массы. Их массивы не содержат
выдуманного массового или топливного профиля. Отклонения старых и новых
эфемерид не включаются в численную невязку краевой задачи.

## «Пазов», физическая ПСИ и общий запуск

```powershell
docker compose run --rm pipeline solve configs/apophis_156kg.json --output runs/apophis
docker compose run --rm pipeline solve configs/venus_156kg.json --output runs/venus
docker compose run --rm pipeline solve configs/venus_156kg.json --output runs/venus --resume
```

`solve` проходит ИРТ → избыток → ограниченное управление «Пазова» → переменная
масса → точная ПСИ → независимая проверка → визуализация сохранённого результата.
Два полных запуска — Апофис и Венера — проверены этим интерфейсом. В `final/`
находятся численные данные, в `plots/` — траектории и профили. `summary.json`
хранит статусы каждого этапа; `completed` выдаётся только после достижения
конечной физической модели и ограничения заданного аппарата.

Для самостоятельных модулей:

```powershell
docker compose run --rm pipeline pazov data/benchmarks/departure/earth_apophis_2029 --output runs/pazov
docker compose run --rm pipeline psi data/benchmarks/pazov/earth_apophis_2029 --output runs/psi
```

Поддерживается `--resume`. У `pazov` можно явно задать `--alpha` для передачи
сглаженного решения в физический модуль. В общем запуске по умолчанию масса
вводится при α=0.5: это общий маршрут, выбранный на четырёх реальных задачах,
после чего смешанный функционал доводится до α=1. Самостоятельный «Пазов»
по умолчанию проходит до α=1 в модели постоянной массы.

Векторизованный закон управления взят из локального компонента «Пазова»;
его исходные скрипты и 36 тестов сохранены. В общем адаптере предел управления
не подбирается вместе с сопряжёнными переменными. Если гладкое ИРТ-решение
превышает заданный предел, он достигается отдельным продолжением. Промежуточное
большее значение явно помечено `hardware_limit_reached=false`.
Путь «ввести массу до завершения снижения предела тяги» реализован как резервный,
но пока не подтверждён полным проходом для длинного перелёта к Церере.

Физическая модель: постоянные F и c, переменная оставшаяся масса,
гравитация центрального тела, фиксированное время и выбранные конечные условия.
Масса нормирована на начальную; состояние — [r,v,m,p_r,p_v,p_m].
Для доли тяги δ и A=F/(m0·единица ускорения), q=F·TU/(m0·c):

\[
J_\alpha=\int[(1-\alpha)(A\delta)^2/2+\alpha A\delta]dt,
\quad \dot m=-q\delta.
\]

При α=1 функционал пропорционален реальному расходу топлива. Массовая
сопряжённая переменная удовлетворяет p_m(tf)=0 в используемой лагранжевой
записи. На массовом продолжении β=0…1 используется явно сохранённая
промежуточная модель; её массовые данные помечены как proxy, пока β<1.

Конечные активные/пассивные дуги решаются с явными временами переключений,
без подмены конечного результата сглаженным управлением. Проверяются конечные
условия, начальное ограничение избытка, трансверсальность, положительная масса,
сухая масса, точная тяга 0/F, знаки функции переключения на дугах и её нули
на стыках. Расход по массе сверяется с F/c, умноженным на суммарное активное время.
Проверяются также сохранённые массовые и тяговые профили, чтобы соответствующий
график не мог расходиться с независимо проинтегрированной траекторией.

При касании ограничения избытка используются дополнительные параметры
«вектор избытка + множитель», без деления на исчезающий p_v(t0). Коллокация
имеет резервную стрельбу; независимое интегрирование может потребовать
ужесточения точности, даже если сама коллокация уже выполнила конечные условия.

Отдельная сверка с **неизменённым Fortran KIAM** использует его уравнения
массово-оптимальной задачи и API управления. Переход от нашей лагранжевой
записи к записи KIAM с p_m(tf)=1:
`p_r,v(KIAM)=p_r,v/vex`, `p_m(KIAM)=1+p_m/vex`, где vex=c/VU.
На четырёх сохранённых траекториях уравнения и управление совпадают до
машинной точности на проверенных внутренних точках.

| Реальный случай | Расход, кг | Независимая ошибка встречи, м |
|---|---:|---:|
| Земля → Апофис | 18.64035 | 0.83 |
| Земля → Марс | 22.89885 | 2.95 |
| Земля → Венера | 27.65200 | 0.96 |
| Земля → Бенну | 32.63107 | 0.71 |

Это проверенные экстремали в заданной модели, не доказанный глобальный
минимум. Все четыре случая используют 156 кг, 25 мН и c=20 км/с;
они не заменяют исторический УММП-эталон с его другим законом двигателя.
Данные — `data/benchmarks/pazov/` и `data/benchmarks/psi/`.
Полные данные и истории двух сквозных сценариев без производных рисунков —
`data/benchmarks/end_to_end/`. Их `final/` можно снова отрисовать командой
`render`; для этого повторная оптимизация не нужна.

Общий `solve` возвращает 0 при полном завершении, 2 при частичном пути и 1
при ошибке. Ошибка внутри принадлежащего ему запуска записывается как
`failed`, а не оставляет устаревший статус `running`. Существующие чужие
каталоги и запуски с другой конфигурацией не перезаписываются.

Общая работоспособность ещё не подтверждена для всей широкой матрицы.
По уточнению пользователя Луна снята из целей метода; её код сохранён как
отдельный эксперимент. Приоритет — планеты и астероиды, включая Цереру.
Частичный проход к Церере сохранён в `runs/psi_ceres_mass_before_limit/`;
после исправления округления насыщенного управления он прошёл прежний барьер
и достиг β≈0.783. Это не конечная ПСИ и не доказанная недостижимость.

## Переход от ПСИ к УММП

```powershell
docker compose run --rm pipeline ummp data/benchmarks/psi/earth_apophis_2029 --output runs/apophis_ummp
docker compose run --rm pipeline verify-ummp runs/apophis_ummp/point_0004
```

На вход подаётся каталог принятой точной ПСИ межпланетного участка в центральном
поле Солнца. Перед продолжением вход проверяется независимо, включая KIAM для
постоянной скорости истечения. Граничные состояния, даты, масса, сухая масса
и режим ограничения стартовой скорости наследуются из входа.
Привязка к локальным орбитальным участкам проверяется отдельно.

На доле `s=0` действуют постоянные F и F/c из ПСИ. На доле `s=1` действуют
тяга и массовый расход исторического двигателя. Обе величины интерполируются
линейно по `s`. Закон УММП учитывает деградацию мощности, зависимость от
гелиоцентрического расстояния, резерв 60 Вт, ограничение мощности 450 Вт
и коэффициент расхода 1,3. Оптимизируется израсходованная масса.
Градиенты тяги и расхода входят в сопряжённые уравнения. Моменты переключений
уточняются на каждом шаге. Результат хранит доступные и фактические тягу и расход.

`summary.json` содержит `last_result`, достигнутую долю и итог независимой
проверки. Использовать `verify-ummp` с путём из `last_result`.
При `partial` читать причины отклонения шагов в `continuation.json`.
`--resume` принимает тот же вход, закон и настройки. Смена числа дуг может
остановить коррекцию на текущей ветви. Ветви, достигающие порога 200 Вт,
требуют гибридных условий и здесь отклоняются.

Контрольная серия заново строит ПСИ для исторических граничных состояний
Апофиса 156 кг, затем продолжает её до УММП. Сохранённое решение УММП
используется для сравнения результатов.

```powershell
docker compose run --rm --entrypoint python pipeline -m trajectory_pipeline.ummp_benchmark --output runs/apophis_ummp_benchmark
```

[Расчёт и сравнение с историческим эталоном](../reports/ummp_apophis_156kg.md).

## Общая матрица и скилы

```powershell
docker compose run --rm pipeline sweep-solve configs/physical_matrix.json --output runs/physical_matrix_common_v1
```

`configs/physical_matrix.json` содержит 15 реальных постановок: Меркурий,
Венера, Марс (две эпохи и пролёт), Юпитер, пролёт Сатурна, обратный перелёт
Венера–Земля; Апофис, Эрос, Бенну, Рюгу, Полигимния, Церера и 2015 RE36.
Одинаковые m0=156 кг, F=25 мН, c=20 км/с, сухая масса 90 кг, начальный избыток
≤3 км/с, допуски 1000 м/0.01 м/с. Настройки выбора ветвей и численные бюджеты
одинаковы. Различаются заданные тела, даты, длительности и конечные условия.
Эта выборка оценивает метод при одном классе аппарата; частичный результат
при ограниченном бюджете не доказывает физическую недостижимость задачи.

`results.json` обновляется после каждого случая и показывает этап остановки,
достигнутую модель и независимые невязки. Полная диагностика лежит в каталогах
случаев. `--resume` проверяет неизменность матрицы; готовые результаты
перепроверяются, частичные продолжаются с checkpoint. Не смешивать серию с
индивидуально настроенными старыми успешными примерами.

Каждый случай запускается в отдельном процессе с журналом и faulthandler;
авария нативной библиотеки не должна останавливать остальную матрицу.
После прерывания серии `--resume --pending-only` сохраняет исходы уже
завершённых попыток и выполняет только оставшиеся случаи. Обычный `--resume`
возобновляет также частичные пути, поэтому он уже даёт им дополнительный
бюджет и должен учитываться отдельно при сравнении первых проходов.

Сводка границ без нового расчёта:
`docker compose run --rm pipeline matrix-report <matrix-run> --output <report.md>`.
Сохраняются Markdown-таблица и JSON со статусами, причинами остановок и SHA256
конечных данных. Статус готовности сверяется с точной физической моделью,
аппаратным пределом и сохранёнными независимыми проверками.

Пять локальных скилов находятся в `.agents/skills/`: `trajectory-pipeline`
(общий сценарий), `trajectory-seed` (ИРТ/начальная скорость),
`trajectory-propulsion` (Пазов/ПСИ), `trajectory-ephemerides`,
`trajectory-visualization`. Скилы вызывают общий CLI и ссылаются на эту
документацию; дублированных миссионных решателей в них нет.

## Сохранённый лунный эксперимент (вне целей метода)

`configs/lunar_high_orbit_250mn.json` и
`data/benchmarks/end_to_end/lunar_250mn/` сохраняют завершённый геоцентрический
сценарий Земля–Луна–Солнце: старт с круговой орбиты радиусом 150 тыс. км,
12 суток, конечное осцулирующее состояние в 20 тыс. км от центра Луны,
250 мН и 156 кг. Начальный импульс 457.96 м/с считается предоставленным
в рамках отдельного ограничения, его топливо в ПСИ не включено.
Расход ПСИ 5.98049 кг, ошибка независимого прибытия 0.036 м; поле сверено
с нативным N-body Fortran KIAM (расхождение около 1.5e-11 м/с²).
Это не сценарий вывода с низкой околоземной орбиты и не доказательство
долговременной устойчивости окололунной орбиты.

В `gravity.py` учтены прямое/косвенное ускорения Солнца/Луны и градиенты;
эфемериды связаны с результатом SHA256. Сближения с Землёй/Луной проверяются
по плотному независимому интегрированию с уточнением локальных минимумов.
Вариант `configs/lunar_high_orbit.json` с 100 мН остался частичным и не
подменён вариантом 250 мН. Дальнейшая лунная приёмка не входит в поручение.

## Проверки

Для расследования программного сбоя можно изолированно повторить следующий
сохранённый сглаженный шаг ПСИ, не пересчитывая ИРТ и не меняя аппарат:

```powershell
docker compose run --rm pipeline diagnose-step <saved-case> --phase fuel --output runs/diagnostic_step --native-prefix
```

Доступны фазы `mass`, `limit`, `fuel`; точный несглаженный шаг этим инструментом
не подменяется. `step.json` хранит исходную миссию, SHA256 входов/кода,
восстановленный пробный параметр, модель, окружение и численные бюджеты.
`--budget-scale` меняет только бюджеты диагностики для медленного инструмента;
такие результаты явно помечены `diagnostic_only` и не включаются в матрицу.
Холодный запуск не воспроизводит всю историю аллокаций исходного процесса.

Для проверки памяти есть отдельный образ с Valgrind, наследующий scientific
runtime и неизменённый KIAM:

```powershell
docker build -f docker/diagnostics.Dockerfile -t trajectory-pipeline:memcheck docker
```

Это диагностика ошибок памяти, не дополнительный проход приёмки или попытка
подогнать несошедшийся случай. Код завершения Valgrind и его журнал проверять
отдельно от `summary.json` численного шага.

Общая коллокация Пазова и массового моста использует аналитические производные
центральных канонических уравнений (`bounded_derivatives.py`). Их проверяют на
сохранённых реальных состояниях разных тел, аппаратных вариантов и фаз:
центральные разности и гамильтонова симметрия. В нецентральном эксперименте
сохраняются численные производные; точные переключения решаются сегментно.
Метаданные коллокации содержат метод производных, число узлов и итераций.
Ключ `analytic_derivatives=False` внутренней функции `collocate` предназначен
для парного сравнения, не для настройки отдельных миссий в матрице.

Это ещё не подтверждает сходимость всей расширенной физической матрицы.
