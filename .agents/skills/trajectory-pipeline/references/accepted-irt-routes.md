# От принятой ИРТ до физической ПСИ: серия и альтернативные пути

Использовать, когда уже есть принятые ИРТ и нужно продолжить их без нового
подбора ILTT. Сохранять исходные массивы и SHA256, дату, цель, режим,
источники орбит, массу, двигатель и предел избытка. Апофис перед физическим
переходом пересогласовать на полные эфемериды, если ранняя ИРТ была кеплеровой.
Сопряжённые остаются основными переменными; переключение на ILTT не требуется.

## Последовательность

1. Повторно проверить ИРТ и её соответствие запросу. Продолжить избыток,
   ограниченное управление Пазова, переменную массу, фактическую тягу и
   топливный функционал до точных активных/пассивных дуг.
2. При отказе сохранять последнюю независимо принятую опору. Попробовать
   совместное продолжение массы и ограничения тяги вместо последовательного.
3. Освободить длительность на промежуточной модели и заново согласовать
   положение цели на новой дате прибытия. Попробовать также возврат к ранней
   опоре: застрявшая поздняя модель не должна быть единственным начальным
   приближением. Указывать допустимый диапазон времени заранее.
4. Если уже достигнуты полная переменная масса и фактическая тяга, пробовать
   точные дуги в декартовых сопряжённых и локальных legacy-R/RTN координатах,
   затем совместную коррекцию дуг и длительности. Для гладкого родителя
   подготовить непроверенное приближение переключений по throttle=0,5
   (`physical_transfer_routes.exact_time_seed`); наличие этих моментов ещё
   не означает принятой ПСИ.
5. Если есть совместимая физическая опора той же цели, режима и аппарата,
   возможен независимый R-перенос на запрошенную дату с коррекцией сначала
   фиксированной, затем свободной длительности. Сохранить ссылку на опору,
   её хеш и матрицу переноса. Это альтернативный путь, а не холодное
   продолжение данной ИРТ и не последовательное продолжение по датам.

Не ослаблять физические допуски ради сходимости. Если путь не завершился,
указывать этап, α/β, фактическую модель тяги, длительность, причину и бюджет.
Отдельно отражать отсутствие совместимой опоры, исчерпание бюджета и отказ
независимой проверки. Изменение длительности и достижение допустимой
траектории не означают доказанного минимума по времени/топливу.

## Физическая приёмка

Требуются α=β=1, заданные F/c, переменная масса и допустимый остаток топлива,
точные дуги, граничные условия и условия оптимальности. Независимо выполнить
`verify_bounded`, `verify_kiam_psi` и `audit_configuration(..., require_final=True)`.
Последний аудит должен сравнивать результат с **исходным запросом**,
разрешая только явно выбранные изменения (например, `tof_days`). Само
соответствие результата собственной metadata недостаточно. Не считать
проверенную промежуточную модель физической ПСИ.

## Воспроизведение серии 42 ИРТ

По умолчанию контроллеры ниже используют фиксированный архив `coordinate_matrix_v1`
(42 принятых из 45 исходных случаев). Это конкретный дизайн проверки,
не общий автоматический перебор произвольных миссий и не новая ветвь ILTT.
Научные операции выполняют существующие общие модули. Для другой серии передать `--sources <manifest.json>` в обеих первых фазах: список объектов `{"case_id":"...","source":"папка_принятой_ИРТ"}` с путями, доступными внутри Docker. Хеши источников фиксируются в дизайне; повторный запуск с другим дизайном запрещён. Дальнейшие маршруты читают этот сохранённый дизайн.

Из корня репозитория, в Docker, последовательно:

```sh
docker compose run --rm -T -e OPENBLAS_NUM_THREADS=1 -e OMP_NUM_THREADS=1 --entrypoint python pipeline -m trajectory_pipeline.accepted_irt_routes --output runs/<new> --phase primary --workers 4
docker compose run --rm -T -e OPENBLAS_NUM_THREADS=1 -e OMP_NUM_THREADS=1 --entrypoint python pipeline -m trajectory_pipeline.accepted_irt_routes --output runs/<new> --phase recover --workers 8
docker compose run --rm -T -e OPENBLAS_NUM_THREADS=1 -e OMP_NUM_THREADS=1 --entrypoint python pipeline -m trajectory_pipeline.physical_transfer_routes --output runs/<new> --workers 8
docker compose run --rm -T -e OPENBLAS_NUM_THREADS=1 -e OMP_NUM_THREADS=1 --entrypoint python pipeline -m trajectory_pipeline.accepted_irt_report --output runs/<new>
```

Каждую фазу завершить перед следующей; не запускать двух писателей одного
случая. Повторный запуск переиспользует принятую физическую ПСИ после проверки.
Журнал этапов связывает вход по содержимому, хранит неизменяемые опоры и
квитанции выхода. После прерывания восстанавливает последнюю проверенную
модель; частичный этап допускает до трёх попыток, с отдельными каталогами.
Проверка конечной ПСИ отличается от проверки гладкой промежуточной модели.
Отчёт также работает на незавершённой серии и читает фактические пути опор;
повторная упаковка создаёт `archive_002/` и далее, сохраняя предыдущие архивы.

Для собственной серии передать `--sources <manifest.json>`: список объектов
`case_id`, `source` и необязательных `settings`, `horizon_days`,
`duration_bounds_days`, `transfer_bounds_days`. Масса, двигатель и источники
берутся из каждого принятого входа; это не контроллер только для 42 строк.
Отчёт показывает фактическую конфигурацию каждого случая.

В дизайне серии первые освобождения ограничены [0,5T;1,5T] и [0,5T;2T],
последний маршрут — [0,5T;max(2T,1095,75 суток)]. Это общие настройки данной
серии, не универсальное физическое ограничение. Двигатель и даты не меняются.
