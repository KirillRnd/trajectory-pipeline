Работать из корня проекта. Сначала читать [текущее состояние](../../../PIPELINE_STATUS.md),
а по нужному режиму — [документацию модулей](../../../trajectory_pipeline/README.md).
Все вычисления выполнять в Docker: `docker compose build pipeline`. Windows Python не запускать.

Для новой задачи описать миссию в JSON, опираясь на `configs/`: тела, центр,
эпоха TDB, время, встреча/пролёт, аппарат, ограничения и допуски. Не подставлять
неизвестные физические условия молча. Проверить покрытие эфемерид до запуска.
Использовать общие функции `trajectory_pipeline`, а не новый частный решатель.

Выбирать состав цепочки по полям миссии:

| Поля | Что рассчитывается | Контроллер |
|---|---|---|
| Без орбитальных полей | Межпланетный участок, без орбитальных участков | `runner.py` |
| `orbital_maneuvers` + `mass_reference="initial_orbit"` | Все четыре сочетания: раскрутка/импульс и скрутка/импульсный захват | `orbital_pipeline.py` |
| `capture` | Перелёт и скрутка на заданную орбиту | `capture_pipeline.py` |
| `parking_departure` | Импульс РБ с круговой НОО, отлёт до сферы Земли и перелёт | `launch_pipeline.py` |
| Оба поля | НОО → РБ → перелёт → конечная орбита | `launch_pipeline.py` + `capture_pipeline.py` |

Для отлёта, захвата или проверки их сшивки читать
[планетные интерфейсы](references/planetary-interfaces.md): параметры, смысл дат,
согласование векторов и массы, сохранённые участки и команды проверки.
Готовый пример всей связки —
[`earth_mars_2030_dec01_leo200_capture.json`](../../../configs/earth_mars_2030_dec01_leo200_capture.json).
Высота НОО настраивается, 200 км — типичное значение, а не общее ограничение.

Способы отлёта и прибытия выбирать независимо через `orbital_maneuvers`:
`departure.kind` и `arrival.kind` равны `spiral` либо `impulse`.
В этом интерфейсе `mass_kg` — масса КА на исходной орбите. После раскрутки
внешняя ПСИ получает уменьшенную массу, а топливо импульсного захвата
перевозится вместе с аппаратом; его c задаётся отдельно от c ЭРДУ.
Примеры — `configs/orbital_modes/`. Начать с
[инструкции четырёх сочетаний](references/planetary-interfaces.md#сочетания-отлёта-и-прибытия).
Прежние `parking_departure`/`capture` сохранены для совместимости и имеют
прежнюю привязку массы к началу перелёта; не смешивать два интерфейса.

Полный расчёт:
`docker compose run --rm pipeline solve <mission.json> --output <new-run>`.
Возобновление той же постановки: та же команда с `--resume`.
Выход 0 означает завершение запрошенного состава цепочки, 2 — частичный путь,
1 — ошибку. Проверять `completion_scope` и `verification.passed`:
межпланетная ПСИ сама по себе не означает отлёт с НОО или выход на орбиту.
Читать `summary.json` и последний checkpoint, а не судить по коду завершившейся
оболочки или наличию рисунка. Вход межпланетной ПСИ фиксируется в `psi_source/`;
при составной миссии искать его и запросы во вложенных этапах.

Параметры межпланетного расчёта связывает `request.json`; `parameter_audit.json` проверяет их
на стыках и перед финалом. Не обходить контроль заменой mission.json или
метаданных старого результата. Для вариаций двигателя/массы/даты использовать
`configs/parameter_study_design.json` и `parameter-report`; оценивать долю
завершений по всем вариантам, а не только лучшие отдельные строки.
В `sweep-solve` передавать `--parameter-design <design>` для проверки
соответствия сгенерированной матрицы плану до первого численного запуска.

Для составной миссии дополнительно проверять `outer_request.json`,
`coupling.json`, SHA256 участков и независимый верификатор всего контроллера
из [инструкции интерфейсов](references/planetary-interfaces.md).
Не переносить старые решённые смещения `departure_offset_state_si` и
`arrival_offset_state_si` в новый запрос вместо нового согласования.
Для `orbital_maneuvers` использовать `verify-orbital <run>` и
`render-orbital <run> --output <plots>` в том же Docker-сервисе.
События импульсов хранятся отдельно в `impulses.json`: проверять закон скачка
скорости/массы, а не требовать их непрерывности в точке включения.

Широкая приёмка: `docker compose run --rm pipeline sweep-solve configs/physical_matrix.json --output <new-series>`.
Не менять единые параметры под отдельные тела. После серии:
`docker compose run --rm pipeline matrix-report <series> --output <report.md>` — таблица и JSON границ,
без повторной оптимизации; обязательно учитывать незавершённые случаи.
`outcome-report <series> --output <report.md>` даёт конкретный остановившийся
блок, бюджет/минимальный шаг/ошибку/аварию и последнюю проверенную модель.
Пользователь допускает несходимость части постановок; не подгонять их ради
полного набора успехов и не выдавать программную ошибку за недостижимость.

Если работа нужна по отдельному блоку, применять соответствующий локальный скил:
`trajectory-seed`, `trajectory-propulsion`, `trajectory-ephemerides`,
`trajectory-visualization`. Сам запрос на разбор готового решения не разрешает
заново оптимизировать его.

ПСИ принимается после β=1, α=1, реального аппаратного предела, независимого
интегрирования, проверки границ/переключений/массы и сверки с KIAM.
Частичный результат с повышенной тягой — только вход продолжения. Несходимость
не доказывает недостижимость, найденная экстремаль не доказывает глобальный минимум.
Для работоспособности метода проверять разные реальные геометрии и тела;
не заменять матрицу повторными настройками одной миссии.
Прежние широкие серии проверяли межпланетную часть. Новые отлёт и захват
пока не прошли широкую совместную приёмку; успешный Марс её не заменяет.

Луна снята пользователем из целей метода. Её отдельный экспериментальный код
сохранён; не расширять лунные сценарии при приёмке планетно-астероидной матрицы.
Не менять KIAM. Не переносить численный результат исторического УММП на новую
модель постоянных F и c: у эталона другой закон двигателя.

При остановке сохранить последний принятый результат и назвать конкретный
незавершённый этап. Перед повтором установить причину и содержательное изменение.
Отчёт: постановка, достигнутая модель, численные невязки, ограничения области
применимости и пути к данным/графикам.
