# Отлёт с РБ и планетоцентрический захват

Читать при работе с `parking_departure`, `capture` и сшивкой орбитальных
участков. Все команды выполняются из корня проекта в Docker.

## Сочетания отлёта и прибытия

Различать способ двух **локальных орбитальных манёвров** и управление
межпланетным участком. «Оба за счёт импульсов» означает импульсный отлёт
и импульсный захват; это само по себе не переводит перелёт на баллистическую
модель. Его модель задаётся отдельно.

| Отлёт | Прибытие | Поддержка общим контроллером |
|---|---|---|
| Раскрутка на малой тяге | Скрутка на малой тяге | `orbital_maneuvers`: `spiral` / `spiral` |
| Импульс РБ | Импульсный захват | `orbital_maneuvers`: `impulse` / `impulse` |
| Раскрутка на малой тяге | Импульсный захват | `orbital_maneuvers`: `spiral` / `impulse` |
| Импульс РБ | Скрутка на малой тяге | `orbital_maneuvers`: `impulse` / `spiral`; также прежняя связка |

Общий вход для четырёх режимов — `orbital_pipeline.py`, локальные новые
законы — `orbital_maneuvers.py`. Прежний `parking_departure` всегда строит импульсный отлёт,
`capture` всегда строит скрутку; поле `departure_mode` задаёт ограничение
начальной скорости межпланетного участка, а не способ орбитального разгона.
Нулевой расход на пассивном участке не делает скрутку импульсным захватом.

Не смешивать новые поля с прежними `parking_departure`/`capture`.
Неподдерживаемый `kind` отклоняется валидацией; не подменять его другим.

Для приёмки сочетаний проверять следующие условия:

- Раскрутка начинается с заданной орбиты отправления. Интегрировать физический
  закон тяги и `dm/dt = -F/c`, согласовывать время, состояние на сфере и
  оставшуюся массу с внешним участком. Простое обращение массива скрутки
  во времени меняет закон массы и не является готовым физическим отлётом.
- Скрутку можно строить назад от конечной орбиты, но принимать после прямого
  пересчёта от фактического внешнего состояния. Раскрутка и скрутка расходуют
  один согласованный запас аппарата, если постановка не задаёт отдельные ступени.
- Для импульсного захвата нужна входящая траектория от интерфейса до точки
  манёвра и заданное состояние конечной орбиты в той же точке. Вычислять
  **вектор** `Δv = vпосле - vдо`; формула разности модулей допустима только
  для доказанно сонаправленных касательных скоростей. Проверять достижение
  точки манёвра, перицентр без столкновения, энергию и конечную орбиту.
- На границе локального и внешнего участка согласовывать положение,
  полный вектор скорости, эпоху и массу одной и той же конфигурации КА.
  В самой точке идеального импульса положение и время непрерывны,
  а скорость имеет **заданный скачок Δv**. Не требовать нулевой невязки
  скоростей до и после импульса; проверять невязку закона этого скачка.
- При расчёте топлива импульсного двигателя проверять массы до/после
  включения по его скорости истечения: `mдо/mпосле = exp(|Δv|/cимп)`.
  Отделение ступени учитывать отдельным событием. ЭРДУ и РБ могут иметь
  разные c и массу оборудования. Если двигатель захвата входит в КА,
  его топливо должно уже присутствовать в массе на межпланетном участке.
  Без параметров импульсного двигателя сообщать требуемую Δv, а не
  выдумывать расход, полную стартовую массу или баланс ступеней.
- Для четырёх сочетаний нужны собственные свидетельства полной сшивки;
  успех существующей комбинации и автономный тест гиперболы их не заменяют.

## Новый общий интерфейс четырёх режимов

Установить `mass_reference="initial_orbit"`: `mass_kg` теперь означает массу
КА на НОО **до раскрутки**, а не на межпланетной границе. Внутренний запрос
внешней ПСИ получает `mass_reference="interplanetary_departure"` и фактическую
остаточную массу; пользователю не подменять этим внутренним запросом миссию.

`orbital_maneuvers.departure` содержит `kind` и параметры исходной круговой
орбиты: `parking_altitude_m`, `planet_radius_m`, `mu_m3_s2`,
`interface_radius_m`, `plane_mode="free"`. Раскрутка использует F/c из
`spacecraft` и прямое интегрирование с убывающей массой. Её независимая
проверка использует другую запись полярных уравнений и другой интегратор;
длинную раскрутку не заменять обращением готовой скрутки во времени.

`orbital_maneuvers.arrival` содержит `kind` и те же размеры конечной орбиты,
что `capture`. При `kind="impulse"` обязательны отдельные
`exhaust_velocity_m_s` импульсного двигателя и `excess_velocity_m_s`
входящей гиперболы. В принятом примере скорость истечения равна 3200 м/с,
избыток — 1000 м/с; это параметры конфигурации, не универсальные константы.
Координаты, все компоненты скорости и масса до/после захвата записаны в
событии `arrival_impulse`. Начальное состояние на сфере — входящая гипербола,
а не связанный апоцентр, используемый существующей скруткой.

Импульсный отлёт по-прежнему моделирует **внешний РБ**: масса полезной нагрузки
не меняется при его включении, топливо РБ не входит в массу КА.
Прибытие импульсом — расход из массы самого КА по заданному c.
Не выдавать этот режим за полную массовую модель КА+РБ с отделением ступени.

При смене свободной начальной скорости на заданное состояние после раскрутки
контроллер заново проходит штатную ИРТ → Пазов → ПСИ. Число активных дуг
старого свободного отлёта нельзя считать неизменным. Финал обязан достигнуть
физических F/c и α=β=1, независимо от использованного приближения.

Примеры и две объявленные единообразные матрицы:
`configs/orbital_modes/matrix_dry90.json` (прежняя сухая масса) и
`matrix_dry60.json` (отдельная контрольная сухая масса 60 кг для всех режимов).
Их результаты не объединять и не выдавать изменение сухой массы за улучшение
сходимости на прежнем аппарате. Раскрутка съедает заметную долю топлива;
отсутствие допустимого финала с сухой массой 90 кг не отменяет проверку
реализации на другой, явно объявленной конфигурации.

```powershell
docker compose run --rm pipeline solve configs/orbital_modes/mars_spiral_impulse_dry60.json --output runs/new_orbital_case
docker compose run --rm pipeline verify-orbital runs/new_orbital_case
docker compose run --rm pipeline render-orbital runs/new_orbital_case --output runs/new_orbital_plots
```

Новый контроллер сохраняет `departure/`, `outer/`, `arrival/`, `final/`,
`request.json`, `outer_request.json`, `impulses.json`, историю согласования
и `verification.json`. В `final/` конечная точка относится к состоянию
**после** захвата, а в `arrival/` при импульсном режиме — до включения.
Разницу задаёт событие; не интерполировать физическую тягу через импульс.
`--resume` проверяет готовый результат либо восстанавливается с принятой
внешней ПСИ; при отсутствии принятого checkpoint явно отказывает.
`solver.orbital_seed_path` — необязательная подсказка. Без неё строится новая
штатная цепочка приближения. Неподходящие даты/тела исходного результата
отклоняются. Все проверки и графики выполняются в Docker.

## Прежний интерфейс parking_departure / capture

Далее описаны сохранённые прежние постановки. В них `mass_kg` относится
к началу межпланетного участка. Для четырёх новых сочетаний применять
`orbital_maneuvers` и массу на исходной НОО, как указано выше.

Примеры конфигураций в корне проекта:

- `configs/earth_mars_2030_dec01_capture_400x30000.json` — перелёт и захват.
- `configs/earth_mars_2030_dec01_leo200_capture.json` — РБ, перелёт и захват.

`parking_departure` задаёт `parking_altitude_m` (типично 200000 м),
`interface_radius_m`, `planet_radius_m`, `mu_m3_s2`, `plane_mode="free"`.
Поддерживается отлёт от Земли с круговой НОО в свободно выбранной плоскости.
Высота задаётся в миссии; 200 км не подставлять вместо принятой пользователем
высоты. РБ моделируется мгновенным касательным импульсом в перигее.
Модуль `parking_departure.py` возвращает Δv, вектор импульса, гиперболу,
пролётное время, скорость на конечном радиусе и истинный избыток v∞.

`capture` задаёт `mu_m3_s2`, `planet_radius_m`, `periapsis_altitude_m`,
`apoapsis_altitude_m`, `interface_radius_m`, `plane="planet_orbit"`,
`interface_side="sunward"`. Высоты отсчитываются от указанного радиуса тела.
Проверять источник μ и радиуса, согласованность единиц и определение интерфейса.
Числа Земли или Марса из примера нельзя переносить на другое тело автоматически.
Сейчас поддерживается прямое движение в орбитальной плоскости планеты,
вход с солнечной стороны в апоцентр связанной орбиты; произвольный
гиперболический вход и фиксированное наклонение не реализованы.

Для полной связки `launch_tdb` означает **выход из сферы Земли**.
Импульс РБ происходит раньше на рассчитанное время отлёта.
`tof_days` отсчитывается от выхода из земной сферы до входа в сферу цели;
скрутка добавляет свою длительность после этого. Проверять эфемериды от
самого раннего импульса до конца скрутки. Если пользователь задал дату
импульса РБ, её нельзя молча записать в `launch_tdb` как дату интерфейса:
нужно согласовать эпоху интерфейса с пролётным временем и пересчитать цепочку.

Двигатель и масса берутся из `mass_kg` и `spacecraft` той же миссии.
Масса КА относится к аппарату после отделения РБ. Δv в м/с не является
импульсом силы в Н·с; топливо и полную массу РБ без его удельного импульса
и сухой массы не вычислять. Расход ЭРДУ не включает топливо РБ.

## Что именно согласовывают контроллеры

`launch_pipeline.py` строит выходящую гиперболу по фактическому **вектору**
скорости внешнего участка, получает положение на конечном радиусе,
пересчитывает межпланетную ПСИ и повторяет согласование.
Ограничение `vinf_max_m_s` остаётся пределом истинного избытка:
скорость на сфере удовлетворяет `vсфера² = v∞² + 2 μ / Rсфера`.
Нельзя использовать эти скорости как взаимозаменяемые или просто приклеить
гиперболу к старому состоянию в центре Земли.

`planetary_capture.py` строит скрутку **назад от перицентра конечного эллипса**
с постоянной поперечной тормозящей тягой, заданными F/c и переменной массой.
До тяги добавляется кеплеров пассивный участок от апоцентра на интерфейсе.
`capture_pipeline.py` пересчитывает внешнюю ПСИ до ненулевых относительных
координат и скорости, подбирает конечную массу скрутки до совпадения входных
масс, затем интегрирует вперёд от фактического конца перелёта.
Первая точка хранит точное входное состояние; не заменять её интерполяцией
на t=0 или дополнительным округлением.

Оба интерфейса локальных и межпланетного участков проверяются по координатам,
трём компонентам скорости, времени и массе; это не точки импульсного изменения
скорости и не события отделения ступеней. Совпадения модулей скорости недостаточно. Скрутка использует
остаточную массу после перелёта; произвольного множителя топлива нет.
При новом согласовании отлёта масса скрутки согласовывается заново.

Начальные приближения — `solver.launch_seed_path` и `solver.capture_seed_path`.
Это проверяемые входы, а не разрешение переносить старые параметры.
При изменении дат, аппарата, тела или режима не оставлять несовместимые
пути к примерам: выбрать соответствующее приближение либо убрать эти
подсказки для построения нового. Численные правила приёмки сохранять.
Смещения `departure_offset_state_si` и `arrival_offset_state_si` вычисляют
контроллеры; не редактировать их и запросы ради принятия старых массивов.

## Запуск, результаты и возобновление

```powershell
docker compose run --rm pipeline solve configs/earth_mars_2030_dec01_leo200_capture.json --output runs/new_leo_capture
```

Та же команда с `--resume` проверяет готовую миссию либо использует
поддерживаемый checkpoint. При захвате поддержано восстановление после
согласования массы; при отлёте — сохранённые итерации согласования.
Не обещать возобновление произвольной точки: при отсутствии нужного
checkpoint контроллер явно отказывает. Сохранять остановку и не затирать
предыдущую серию. Бюджет и несходимость не доказывают недостижимость.

| Состав | Где искать данные |
|---|---|
| Захват без РБ | `outer/`, `capture/`, `final/`, `outer_request.json`, `coupling.json` |
| Отлёт с РБ | `launch/`, `final/`, `coupling.json`; `summary.downstream_folder` указывает принятую папку `match_NN/` |
| РБ и захват | В принятом `match_NN/` лежат `outer/`, `capture/`, `final/`, запрос внешней ПСИ и проверка захвата |

Читать `summary.json`, `verification.json`, контрольные суммы и историю
`coupling.json`. Остановку уточняют `launch_phase` или `capture_phase`,
`stop_kind`, `error`; вложенный summary показывает остановившуюся часть.
Готовность определяется всей запрошенной областью `completion_scope`,
а не наличием одного принятого межпланетного участка.

## Проверка сохранённого результата без оптимизации

Для захвата без РБ:

```powershell
docker compose run --rm --entrypoint python pipeline -c "from trajectory_pipeline.capture_pipeline import verify_capture_mission; c=verify_capture_mission('data/benchmarks/examples/earth_mars_2030_dec01_capture_400x30000'); print(c); assert c['passed']"
```

Для РБ с перелётом, включая связку с захватом:

```powershell
docker compose run --rm --entrypoint python pipeline -c "from trajectory_pipeline.launch_pipeline import verify_launch_mission; c=verify_launch_mission('data/benchmarks/examples/earth_mars_2030_dec01_leo200_capture'); print(c); assert c['passed']"
```

Эти функции выполняют независимый численный пересчёт и проверки сохранённых
участков, не оптимизацию. Отдельный `verify_kiam_psi` применим к внешней ПСИ;
успех KIAM для неё не подтверждает всю составную миссию автоматически.
Сопоставлять заданные F/c и массу, вектор импульса с круговой скоростью,
оба интерфейса, конечные радиусы орбиты, баланс расхода и SHA256 источников.

Модель — сопряжённые центральные поля. N-body, J2, тени, конечное горение РБ,
космодром и фиксированная плоскость НОО в эти модули не включены.
Совместная глобальная оптимальность не доказана. Старые широкие серии
относились к межпланетной части; новая матрица четырёх способов манёвра
на Марсе тоже не является широкой приёмкой по разным телам и геометриям.
Первичные свидетельства и ограничения — `reports/examples/mars_dec2030_leo200.md`
и `reports/examples/mars_dec2030_capture.md` в корне проекта.
